# 企业文档法规审核 Skill 设计规格

## 目标

创建一个开源、可插拔法规包驱动的 Codex skill，用于审核企业内部文档。用户提供 `.docx` 文档、适用地区/行业和法规来源配置后，skill 输出可追溯的审核报告，并按需生成带批注或高亮的 `.docx` 副本。

首版不提供法律意见。所有结论必须绑定可定位的法规证据；无法确认法规适用性或原文依据时，标记为“需人工确认”。原始文件不得被覆盖。

## 使用流程

1. 识别输入文档、适用司法辖区、行业、文档类型和期望输出。
2. 读取本地法规包；对缺失或过期的依据，仅从配置的官方来源检索，并记录 URL、标题、版本/发布日期和访问日期。
3. 提取文档段落、表格和标题，保留稳定的段落/字符定位。
4. 按法规包中的审核规则进行逐条比对，输出事实证据、风险分类、置信度和建议改写。
5. 生成 Markdown 与 JSON 报告。
6. 若输入是可编辑 `.docx` 且定位可靠，复制原文件后添加批注/高亮；任何无法安全定位的项目只保留在报告中。
7. 汇总覆盖范围、未检查内容、法规来源和人工复核事项。

法规包由使用者维护，不随 skill 捆绑具体法律内容。示例法规包可作为测试夹具，但不得被描述为完整法规库。

## 法规包

法规包采用版本化 YAML/JSON。每条规则包含唯一 `rule_id`、适用范围、检查说明、法规引用数组和风险默认值。每个引用至少包含 `title`、`issuer`、`jurisdiction`、`effective_date`、`source_url` 或本地文件路径、`locator`（章节/页码/条款）和 `retrieved_at`。规则必须声明是否允许联网补充；联网只能访问配置的官方域名。

规则允许使用关键词、正则或语义检查提示，但语义判断不能替代法规原文证据。法规包加载时校验 schema、日期和引用完整性，并报告冲突或过期规则。

## 审核报告

每个发现包含：稳定 `finding_id`、文档定位、原文摘录、问题摘要、状态（`明确违反`、`疑似风险`、`信息不足`、`通过`）、风险等级（低/中/高/严重）、置信度、法规引用、理由、建议文本、是否已写入 DOCX 标注，以及人工复核说明。

报告顶层包含输入文件摘要、审核配置、法规包版本、来源清单、覆盖率、统计汇总和生成时间。JSON 是机器可读的事实来源，Markdown 是面向人的渲染结果；两者字段保持一致。

## DOCX 标注

原文件复制到新路径后处理。优先使用 OOXML 注释；若文档或依赖不支持可靠批注，则使用高亮加短注释，或跳过标注并记录原因。定位以段落索引、文本哈希和字符范围联合确认，避免同文重复句误标。不得重排正文、删除内容或覆盖原文件。标注文本使用固定前缀：`[法规审核][风险等级] finding_id`，正文放在批注中。

## 隐私与安全

默认只读本地文件；联网检索须由用户配置并明确记录。不得把完整企业文档发送到非官方或未配置服务。日志避免输出敏感原文，临时文件使用任务目录并在成功后清理。报告中可配置脱敏模式。

## 错误处理

- 文档无法解析：停止标注，输出可诊断错误和已完成的来源检查。
- 法规包无效：拒绝执行实质审核，指出具体 schema 错误。
- 来源不可访问：保留本地依据，相关发现降级为“需人工确认”。
- 定位不稳定：报告照常生成，但不写入该条 DOCX 标注。

## 验证策略

提供最小测试夹具：包含普通段落、表格、重复文本、中文标点和已有批注的 DOCX；一组法规包 schema 正反例；以及预期报告 fixture。脚本测试覆盖文本提取、定位稳定性、标注不覆盖原文件、引用完整性和报告 schema。验证命令使用 skill creator 提供的 `quick_validate.py`，脚本另行执行代表性样例。

## 非目标

- 不构建长期运行的法规数据库或 SaaS 后端。
- 不保证穷尽所有适用法律，也不替代律师审查。
- 首版不承诺 PDF 原位批注；可先转文本并仅输出报告。
